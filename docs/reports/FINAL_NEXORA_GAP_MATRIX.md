## 1. Status & Severity Definitions

### Status Classifications
- **`VERIFIED COMPLETE`**: Fully implemented in backend, connected to frontend, backed by automated tests, and verified in active runtime/code.
- **`ARCHITECTURE READY`**: Backend and frontend architecture, data contracts, state machines, and interfaces are fully built and unit tested; awaits live external hardware/vendor credentials (e.g., live OLT SNMP, live bank API keys) during ISP pilot deployment.
- **`STUB`**: Functional abstraction/driver returns simulated success or mock responses for development/sandboxing.
- **`PARTIAL`**: Implemented in part (e.g., backend complete but dedicated UI page missing, or vice versa).
- **`MISSING`**: Required feature is not implemented.
- **`BROKEN`**: Feature exists but throws unhandled errors or fails tests.
- **`BLOCKED`**: Feature cannot be implemented without prerequisite external systems.

### Severity Classifications
- **`P0 (Blocker)`**: Critical security vulnerability, data loss, tenant leak, or financial balance violation that prevents any commercial operation.
- **`P1 (High)`**: Major operational or functional limitation requiring explicit disclosure or immediate operational workaround before pilot onboarding.
- **`P2 (Medium)`**: Secondary workflow enhancement, minor UI polish, or automated convenience feature that can be addressed during routine iteration.
- **`P3 (Low)`**: Cosmetic refinement, documentation note, or optional configuration tuning.
